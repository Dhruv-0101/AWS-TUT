34. ❓ Interview Questions

Q1. What is EC2?

Answer:

Amazon EC2 is an AWS service that provides resizable virtual compute capacity, allowing applications to run on virtual servers in the cloud.

Q2. What is an AMI?

An AMI is a template used to launch EC2 instances, containing the operating system and other required configuration.

Q3. AMI vs Instance?

AMI is the template; an EC2 instance is the running virtual machine created from that template.

Q4. What is a security group?

A security group is a virtual firewall that controls allowed network traffic for an EC2 instance.

Q5. What is a key pair?

A key pair consists of a public key and private key used for secure authentication to an EC2 instance.

Q6. Public IP vs private IP?

A public IP provides public network connectivity, while a private IP is used for communication within private AWS networking.

Q7. What is EBS?

EBS is AWS block storage that can be attached to EC2 instances and is commonly used for their persistent disks.

Q8. What is User Data?

User Data allows initialization scripts or commands to run when an EC2 instance launches.

26. 🔥 Important Interview Concept — Availability Zones

The video then moves to an important AWS concept.

Suppose you're using:

The region contains multiple Availability Zones.

Conceptually:

Mumbai Region
│
├── AZ 1
├── AZ 2
└── AZ 3

Availability Zones are separate infrastructure locations within an AWS Region.

27. Why Multiple Availability Zones?

The reason is resilience and fault isolation.

Suppose:

AZ-A
  ↓
Your EC2

has a major infrastructure problem.

If everything is in one AZ:

Application
     ↓
AZ-A
     ↓
💥

your application can become unavailable.

Instead, you can architect:

              Application
              /         \
             ↓           ↓
           AZ-A         AZ-B
             ↓           ↓
           EC2          EC2

Now failure of one AZ doesn't necessarily take down the entire application.

28. 🧠 The Interesting AWS Account Detail

The instructor asks a very good question:

If every AWS customer sees Availability Zones like ap-south-1a, ap-south-1b, and ap-south-1c, does ap-south-1a physically refer to the exact same Availability Zone for everyone?

Answer:

No.

AWS maps Availability Zone names independently for different AWS accounts.

So:

Your Account
ap-south-1a → Physical AZ X

while another account might have:

Another Account
ap-south-1a → Physical AZ Y

The instructor explains exactly this mapping behavior in the transcript.

29. 🚨 Why Does AWS Do This?

AWS does this so that customers don't unintentionally concentrate their workloads in the same physical Availability Zone merely because they selected the same AZ letter.

Therefore:

ap-south-1a in your account isn't guaranteed to be the same physical AZ as ap-south-1a in another AWS account.

This is a genuinely useful interview concept.

1. 🧠 What is a Security Group?

A Security Group is a virtual firewall that controls incoming and outgoing network traffic for your EC2 instance (specifically at the Network Interface / ENI level).

The primary mental model demonstrated in the video is:

Internet Client / Attacker
            │
            ▼
     Security Group (Virtual Firewall)
  [ Checks Inbound Rules & Ports ]
            │
      ┌─────┴─────┐
      ▼           ▼
   ALLOWED     BLOCKED
   (Port 80)  (Port 22 from unknown IP)
      │           │
      ▼           ▼
 EC2 Instance  Dropped Before Reaching Instance!

If a request arrives on a port or IP that is not allowed in the Security Group, the firewall drops the traffic before it ever reaches your EC2 instance.

2. 🔄 Inbound vs Outbound Rules

Security Group rules are split into two directions with respect to the EC2 instance:

  • Inbound Rules (Incoming Traffic): Controls traffic trying to reach your EC2 instance from external sources.
    🔴 Default state: EMPTY (All incoming traffic is BLOCKED by default).
  • Outbound Rules (Outgoing Traffic): Controls traffic initiated from inside the EC2 instance going out to the internet or other servers.
    🟢 Default state: ALL TRAFFIC ALLOWED (0.0.0.0/0).

Stateful Nature: Security Groups are stateful firewalls. If an inbound request is allowed (e.g. HTTP request on port 80), the response traffic is automatically allowed to return to the client regardless of outbound rules.

3. 🚨 ALLOW Rules Only (No DENY Rules!)

The instructor strongly emphasizes this critical AWS Security Group concept:

Security Groups ONLY support ALLOW rules. You CANNOT write an explicit DENY / BLOCK rule!

Why is this important?

Imagine your web application is under a severe DDoS attack from a specific IP address (e.g., 203.0.113.45). You want to block ONLY that malicious IP while leaving the rest of the world allowed.

❌ You CANNOT block that single IP inside a Security Group because Security Groups do not have a "Deny" rule option.

💡 How to solve this in Production?

To block specific IP addresses in AWS, you must use a Network ACL (NACL) at the VPC Subnet level, or an AWS WAF (Web Application Firewall). Security Groups only define what is permitted.

4. 🌐 Source Options (Anywhere vs My IP)

When defining an Inbound rule, you specify the allowed Source:

  • Anywhere-IPv4 (0.0.0.0/0): Allows traffic from any IPv4 address globally across the entire internet. Suitable for public web servers (Port 80/443).
  • My IP: AWS automatically detects your current workstation public IP address (e.g. 49.207.x.x/32). Best practice for administrative ports like SSH (Port 22).
  • Custom CIDR / Security Group ID: Restricts traffic to specific subnet ranges, or references another Security Group ID (e.g., allowing `App-SG` to connect to `DB-SG` on MySQL port 3306).

2. 🏷️ Model 1 — On-Demand Instances

How it works: You pay for compute capacity by the second with no long-term commitment or upfront payment. You can launch or terminate instances at any time.

Billing Rules Explained by Instructor:

  • Linux & Windows Instances: Billed per-second with a minimum baseline of 1 minute (60 seconds).
    • Run instance for 20 seconds ──► Billed for 60 seconds (1 full minute).
    • Run instance for 80 seconds ──► Billed for 80 seconds.
  • Enterprise OS (RHEL / SUSE): Billed per-hour.

When to use:

  • Short-term workloads (recording a tutorial, running a 30-minute test script)
  • New applications with completely unpredictable traffic loads

3. 📅 Model 2 — Reserved Instances (RI)

How it works: You commit to a specific instance configuration for a 1-Year or 3-Year term in exchange for up to 72% discount compared to On-Demand rates.

Factors Influencing Discount Rate:

  1. Term Length: 3-Year commitment gives significantly higher savings than 1-Year.
  2. Payment Option:
    • All Upfront (AU): Maximum discount (pay full 1/3 year commitment initially).
    • Partial Upfront (PU): Moderate discount + small monthly payments.
    • No Upfront (NU): Lowest RI discount, billed monthly with zero initial payment.
  3. Reservation Attributes: Region, Instance Type/Family, Operating System.

4. 🔄 Standard RIs vs Convertible RIs

When purchasing Reserved Instances, you choose between two flexibility classes:

Feature Standard Reserved Instance Convertible Reserved Instance
Max Discount Up to 72% Up to 65% - 66%
Change Instance Family? ❌ No (Locked to e.g. t2) ✅ Yes (Can upgrade e.g. t2.small → c5.large)
Change OS / Tenancy? ❌ No ✅ Yes
Price Difference Fee N/A Pay only the price delta if upgrading to higher spec

5. 🏨 Model 3 — Spot Instances & Hotel Analogy

How it works: AWS sells unutilized spare EC2 compute capacity at steep discounts (up to 90% off On-Demand prices!).

The Instructor's Hotel Analogy:

Imagine a hotel with 25 rooms. 20 rooms are occupied at $1,000/night, leaving 5 empty rooms. You walk up to the manager and offer $100 for an empty room. The manager accepts $100 to earn extra cash, but warns:

"You can stay as long as the room is empty. But the second a full-paying $1,000 customer walks in, I will throw you out and give them the room!"

6. ⚡ Spot Bidding & 2-Min Warning

Bidding & Interruption Behavior:

  • You set a maximum bid price. As long as spare capacity exists below your bid, your Spot Instance runs.
  • When AWS needs the capacity back for On-Demand users or someone outbids you, AWS sends a 2-minute notification warning (spot-instance-interruption-notice) before forcibly terminating or stopping your instance!

When to use Spot Instances:

🟢 Fault-tolerant, stateless, or batch workloads (e.g. 4-hour batch test suite runs, container worker nodes in EKS/ECS clusters, Big Data Spark jobs, CI/CD build runners).

❌ NEVER use Spot Instances for: Production databases, stateful web apps, or critical single-point-of-failure servers!

7. 🔒 Model 4 — Dedicated Hosts

How it works: Provides a physical EC2 server fully dedicated to your AWS account. You have full visibility and control over sockets and physical CPU cores without sharing hypervisor hardware with other AWS tenants.

Top 2 Production Use Cases Explained by Instructor:

  1. Strict Regulatory / Security Compliance: Industries (finance, healthcare, defense) requiring isolated single-tenant physical hardware.
  2. BYOL (Bring Your Own License): Using existing corporate software licenses bound to physical socket or core counts (e.g. legacy Oracle DB, Windows Server, SQL Server per-core licenses).

8. 💳 Model 5 — AWS Savings Plans

How it works: Modern cost-savings model based on a commitment to a consistent hourly spend (e.g. committing to spend $10/hour for 1 or 3 years).

Discount: Up to **72% discount** (identical to Reserved Instances).

Key Advantage over RIs:

While Reserved Instances lock you into specific instance families, Compute Savings Plans automatically apply discounts across EC2 instance families, regions, OS, and even serverless compute engines like **AWS Fargate** and **AWS Lambda**!

6. 🔐 IMDSv1 vs IMDSv2 Upgrade & Token Architecture

❓ Matlab Hum Use Hi Kyun Karte Hain Isse? (Why Do We Need This?)

1. Instance Metadata (`169.254.169.254`): EC2 server ke andar running OS ko Shuruat me apne Public IP, Instance ID, Zone, ya IAM Roles ka pata nahi hota. Web apps aur User Data scripts ko bina passwords hardcode kiye apne hi server ki jankari mil sake—isliye 169.254.169.254 magic IP use karte hain.

2. Session Token (IMDSv2): Old IMDSv1 me direct curl http://169.254.169.254/... chalane se Hackers SSRF Attack karke aapke AWS Passwords/Keys chura sakte the! IMDSv2 Token "Pehle Token Lo, Phir Metadata Paao" (Two-Step Handshake Guardrail) enforce karta hai jisse Hackers ka attack 100% block ho jata hai!

Why Does IMDSv2 Exist? (Vulnerability & Upgrade Rationale)

IMDSv1 (Legacy Method Shown in Video): Uses simple unauthenticated HTTP GET requests (e.g. curl http://169.254.169.254/latest/meta-data/). Because no headers or tokens are required, IMDSv1 is vulnerable to Server-Side Request Forgery (SSRF) attacks, misconfigured WAFs, open HTTP reverse proxies, and Layer 4 NAT traversal leaks.

IMDSv2 (Modern AWS Production Standard): Introduces session-oriented, token-backed authentication. Every request requires a valid, short-lived session token passed in the X-aws-ec2-metadata-token HTTP header.

WHAT IS THE IMDSv2 SESSION TOKEN?

The token is a temporary, cryptographically signed secret session key generated by the local EC2 hypervisor. It is valid for a configurable Time-To-Live (TTL) ranging from 1 second up to 6 hours (21,600 seconds), and is strictly bound to the specific EC2 instance connection.

🚨 SSRF Hacker Attack Scenario (Why Tokens Block Hacking)

Suppose a web application has a download URL endpoint: http://mywebsite.com/download?url=http://example.com/image.jpg

  • Under IMDSv1 (Vulnerable): Hacker inputs http://mywebsite.com/download?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ → The web server fetches raw AWS Secret Access Keys and leaks them to the hacker! (Real case: 2019 Capital One breach).
  • Under IMDSv2 (Protected): AWS requires a preliminary PUT request with custom TTL headers to issue a Token. Because web application URL fetch proxies CANNOT issue PUT requests or inject secret token headers, the hacker's SSRF attempt is 100% BLOCKED!

💡 Real-World Use Cases of IMDSv2 Session Tokens

  • 1. SSRF Attack Mitigation (Capital One Style Breach Protection): Neutralizes malicious web request proxy traversal instantly.
  • 2. Secure IAM Role Credential Extraction: SDKs and CLI tools on EC2 fetch short-term STS credentials for attached IAM Roles (e.g. S3 access) using token-authorized metadata endpoints.
  • 3. Dynamic Infrastructure Bootstrapping (User Data Scripts): Auto-scaling scripts query their own Public IP, Private IP, Instance ID, Availability Zone, and Subnet ID securely during server startup.
  • 4. Container & Microservice Security Isolation: Enforces network hop limits (HttpPutResponseHopLimit = 1), preventing unauthorized Docker containers or Kubernetes pods from hopping to the host node's metadata service.

1. 💾 SAN Storage Analogy

The instructor explains the core SAN (Storage Area Network) concept:

Think of an EBS volume as a virtual hard drive or USB flash drive connected over a dedicated high-speed network. Compute (EC2 CPU/RAM) and Storage (EBS) reside on physically separate hardware in AWS data centers!

2. 🚀 Root vs Secondary Volumes

Volume roles in EC2 instance architecture:

  • Root Volume: Stores the Operating System boot files (`/` in Linux, `C:` drive in Windows).
  • Secondary Data Volumes: Additional EBS drives mounted for databases, log files, media storage (`/var/log`, `D:` drive).
  • A single EC2 instance can have multiple secondary EBS volumes attached simultaneously.

3. ⚡ EBS Network Latency

Because EBS data travels over the internal AWS data center network between compute and storage servers, read/write I/O operations incur a slight network latency (measured in milliseconds).

For 99.9% of web applications, this latency is negligible. However, for ultra-high-speed in-memory caches, Instance Store is preferred.

4. 📍 AZ Scope Lock Rule

Availability Zone Binding: An EBS volume created in Availability Zone ap-south-1a can ONLY be attached to an EC2 instance residing in ap-south-1a.

How to move an EBS volume to another AZ:

1. Take a Snapshot of the EBS volume in ap-south-1a
2. Restore the Snapshot as a new EBS volume specifying target AZ ap-south-1b
3. Attach new volume to EC2 instance in ap-south-1b

5. 📏 Dynamic Resizing

AWS Elastic Volumes feature allows you to increase the volume size (e.g., from 10 GB to 150 GB) dynamically in the AWS Console **without stopping or rebooting the EC2 instance**!

🟢 Ideal Use Cases: In-memory caches (Redis, Memcached), temporary scratchpads/buffers, stateless load test runners, Hadoop HDFS temporary blocks.

10. 📌 Persistent /etc/fstab Automount

The Reboot Problem: Executing `mount /dev/nvme1n1 /test` is temporary. If the server reboots, the volume will NOT be mounted automatically.

The Solution (Automount via `/etc/fstab` using UUID):

  1. Find the volume's unique UUID: 
    sudo blkid /dev/nvme1n1
# Output: /dev/nvme1n1: UUID="a1b2c3d4-5678-90ab-cdef-1234567890ab" TYPE="ext4"
  2. Add entry to /etc/fstab: 
    UUID=a1b2c3d4-5678-90ab-cdef-1234567890ab  /test  ext4  defaults,nofail  0  2
  3. Test `/etc/fstab` configuration without rebooting: 
    sudo mount -a

Why use UUID instead of `/dev/nvme1n1`? Device names like `/dev/nvme1n1` can change upon instance reboot, whereas UUIDs remain 100% constant!

AWS Tutorials - 27 - How to Resize ROOT EBS Volume

1. 🧠 Secondary vs Root Resizing Architecture

Understanding why Root Volume resizing is different from Secondary Volume resizing:

  • Secondary Volume (e.g. nvme1n1 / xvdf): Formatted directly on raw block device with no partition table. Resizing requires only 2 steps (Console Modify → resize2fs /dev/nvme1n1).
  • Root Volume (e.g. nvme0n1 / xvda): Contains an OS Partition Table (nvme0n1p1 / xvda1 mounted at /). The filesystem lives INSIDE partition 1. Therefore, you MUST grow the partition table first before growing the filesystem!

2. 📐 3-Step Root Resizing Framework

Step 1 (AWS SAN Layer): AWS Console → EC2 → Volumes → Modify Root Volume (8 GiB → 16 GiB).

Step 2 (Linux Partition Layer): Expand OS partition 1: sudo growpart /dev/nvme0n1 1 (or sudo growpart /dev/xvda 1).

Step 3 (Linux Filesystem Layer): Expand filesystem inside partition: sudo resize2fs /dev/nvme0n1p1 (or sudo xfs_growfs -d /).

3. 🖥️ Step 1 — Console Root Expansion

Console actions demonstrated by the instructor:

  1. AWS Console → EC2 → Instances → Select Instance → Storage Tab.
  2. Click the Root Volume ID (e.g. vol-0a1b2c... attached to /dev/sda1 / xvda).
  3. Click Actions → Modify Volume.
  4. Change Size from 8 → 16 GiB → Click Modify.

4. 🔍 Inspection Discrepancy (parent vs partition)

SSH into your EC2 instance and run lsblk:

lsblk

# Modern Nitro Output (t3, c5, m5, Ubuntu 22/24):
NAME        MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
nvme0n1     259:0    0   16G  0 disk                <-- Parent device shows 16GB!
└─nvme0n1p1 259:1    0    8G  0 part /              <-- Partition 1 is STILL 8GB!

# Legacy Xen Output (t2.micro):
NAME    MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
xvda    202:0    0   16G  0 disk                <-- Parent device shows 16GB!
└─xvda1 202:1    0    8G  0 part /              <-- Partition 1 is STILL 8GB!

The parent SAN drive expanded to 16G, but root partition 1 is still capped at 8G!

5. ⚠️ Why resize2fs Fails First

If you skip Step 2 and try running `resize2fs` directly on the partition:

# Nitro:
sudo resize2fs /dev/nvme0n1p1

# Xen:
sudo resize2fs /dev/xvda1

# Output:
# The filesystem is already 2096891 (4k) blocks long. Nothing to do!

Why? Because resize2fs cannot grow a filesystem beyond the boundaries of its partition! You MUST expand partition 1 first using `growpart`!

6. ⚙️ Step 2 — Expand Partition (growpart)

Run the Linux partition table expansion command:

# Nitro Instances:
sudo growpart /dev/nvme0n1 1

# Xen Instances:
sudo growpart /dev/xvda 1

# Output:
# CHANGED: partition=1 start=2048 old: size=16775135 new: size=33552351

# Verify with lsblk (Nitro):
NAME        MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
nvme0n1     259:0    0   16G  0 disk
└─nvme0n1p1 259:1    0   16G  0 part /              <-- Partition 1 is NOW 16GB!

7. 🚨 Critical growpart Syntax

Pay close attention to the syntax required by `growpart`:

❌ INCORRECT: sudo growpart /dev/nvme0n1p1 or sudo growpart /dev/xvda1 (Passing partition path directly will fail!).

✅ CORRECT (Nitro): sudo growpart /dev/nvme0n1 1 (Space between parent disk /dev/nvme0n1 and partition 1!).

✅ CORRECT (Xen): sudo growpart /dev/xvda 1 (Space between parent disk /dev/xvda and partition 1!).

Now that partition 1 is expanded, run `resize2fs` to expand the ext4 filesystem:

sudo resize2fs /dev/nvme0n1p1

# For Xen Instances:
sudo resize2fs /dev/xvda1

# Verify usable root filesystem capacity:
df -h /

If your Root Volume uses an XFS filesystem (default in Amazon Linux 2023 / RHEL):

Instructor Gaurav Sharma's Real-World Virtualization Analogy:

If my configuration crashes the machine, I instantly restore the VM to the previous snapshot state. In AWS, an EBS Snapshot does the exact same thing for your cloud block storage!"

2. 🛡️ 4 Key Use Cases for EBS Snapshots

1. Disaster Recovery & Data Safety: Protection against accidental file deletion (`rm -rf`), database corruption, rogue deployments, or server crashes.

2. Overcoming AZ Scope Lock: EBS volumes are locked to 1 AZ (`ap-south-1a`). Snapshots allow you to create new volumes in `ap-south-1b` or any other AZ!

3. Custom AMI Blueprints: Snapshots serve as the root volume image when creating Amazon Machine Images (AMIs) for Auto Scaling.

4. Compliance & Automated Backups: Scheduled retention policies via AWS Data Lifecycle Manager (DLM).

3. 🏗️ Storage Scope (AZ Lock Volume vs Regional S3 Snapshot)

Architectural distinction between EBS Volume storage vs Snapshot storage:

  • EBS Volume Scope: Bound strictly to a single Availability Zone (e.g. ap-south-1a).
  • Snapshot Storage Scope: Stored under the hood in Amazon S3 (Simple Storage Service). S3 is a Region-level service spanning all AZs in the Region!
    • Snapshots inherit S3's 99.999999999% (11 9's) durability!
    • You don't manage the S3 bucket directly—AWS manages the underlying S3 storage infrastructure for you.

4. ⚡ Incremental Snapshot Architecture Explained

AWS EBS Snapshots use an Incremental Backup Model to optimize speed and cost:

  1. Snapshot #1 (Baseline Full Backup): Copies 100% of the modified data blocks on the disk (e.g. 50 GB data on a 100 GB volume).
  2. Snapshot #2 (Incremental Delta): Two days later, 10 GB of new data is added. Snapshot #2 ONLY copies the 10 GB of changed data blocks! Unchanged data blocks from Snapshot #1 are referenced via metadata pointers.
  3. Snapshot #3 (Incremental Delta): 5 GB of new data added. Snapshot #3 ONLY stores the new 5 GB delta!

5. 💰 Cost Savings Math (Deltas vs Full Backups)

Comparing Full Backup vs Incremental Backup costs in AWS S3 storage:

If AWS Used Full Backups:
• Day 1: 50 GB snapshot
• Day 2: 60 GB snapshot
• Total Billed S3 Storage = 50 + 60 = 110 GB! (Extremely expensive!)

AWS Incremental Backup Reality:
• Day 1: 50 GB baseline snapshot
• Day 2: 10 GB delta snapshot
• Total Billed S3 Storage = 50 + 10 = ONLY 60 GB! (Saves 45%+ in storage costs!)

6. 🧩 Deleting a Snapshot in a Chain

Instructor's Deep Dive Question: "If Snapshot #1 is the baseline containing 50 GB, what happens if I delete Snapshot #1? Will Snapshot #2 break or lose data?"

AWS Internal Block Consolidation Mechanism:

  • When you delete Snapshot #1, DATA IS NOT LOST!
  • AWS automatically identifies which data blocks in Snapshot #1 are still needed by Snapshot #2.
  • AWS consolidates and moves those required data blocks into Snapshot #2 behind the scenes, and only purges blocks that are no longer referenced by any remaining snapshot!
  • Golden Rule: Deleting a snapshot in an incremental chain ONLY deletes data blocks that are unique to that specific snapshot and not needed by subsequent snapshots!

7. 🔄 Cross-AZ Volume Mobility via Snapshots

How to move storage across Availability Zones:

EBS Volume (ap-south-1a) ──► Take Snapshot (S3 Region Level) ──► Create EBS Volume (ap-south-1b)

Because snapshots are stored at the Region level, you can create a new EBS volume from a snapshot in ANY Availability Zone within that Region!

8. 🌍 Cross-Region Disaster Recovery Copying

Snapshots can be copied across AWS Regions (e.g. ap-south-1 Mumbai → us-east-1 N. Virginia) to build Multi-Region Disaster Recovery architectures or deploy applications globally.

9. ⚙️ Automated Lifecycle Management (AWS DLM / AWS Backup)

Instead of creating snapshots manually in the console, production environments use AWS Data Lifecycle Manager (DLM) or AWS Backup to automate snapshot creation, schedule daily/hourly backups, and auto-delete old snapshots after 30/90 days.

1. 🔒 Data at Rest vs Data in Transit Encryption Architecture

1. Data at Rest (SAN Storage): All data blocks written to the underlying EBS SAN storage servers inside AWS data centers are encrypted using AES-256 with KMS keys.

Encrypted Volume Create Snapshot Encrypted Snapshot ❌ Mandatory (Greyed out)

ALB evaluates rules in order of Priority (from lowest priority number to highest). The first rule whose condition matches the request is executed. If no rule matches, the Default Rule is executed.

5. 💤 What is EC2 Instance Hibernation? (RAM Preservation to EBS Disk)

How Hibernation Works:

RAM State Saved to Disk:

When you Hibernate an instance, AWS dumps the entire RAM state (in-memory processes, cache, connection state) into an encrypted file on the EBS root volume before shutting down. Upon Start, AWS reloads the RAM file back into physical RAM, resuming execution from the exact millisecond it was stopped!

6. 📊 Hibernation vs Classic PowerOff / Stop (Technical Comparison Matrix)

Attribute Classic Stop (Power Off) Instance Hibernation
RAM State (Volatile Memory) Wiped clean to 0 (RAM lost) Saved to Encrypted EBS Root Volume file
OS Boot Sequence Cold Boot from scratch Instant Resume from exact RAM state
Linux `uptime` Output Resets to 0 min Preserves accumulated runtime (e.g. 4 min)
Storage Requirement Standard EBS Volume Encrypted EBS Root Volume > RAM Size

7. ⚙️ Prerequisites for Enabling EC2 Hibernation (EBS Encryption & RAM Ratios)

  • Root volume must be an **EBS volume** (Instance Store not supported).
  • EBS Root Volume must be **Encrypted** (AWS KMS key).
  • EBS Root Volume size must be large enough to hold RAM contents + OS files.
  • Supported Instance Families: C3, C4, C5, M3, M4, M5, R3, R4, R5, T2, T3 (HVM AMIs).
